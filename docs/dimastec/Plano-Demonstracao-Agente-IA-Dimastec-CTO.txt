1. Objetivo da demonstração

Demonstrar ao CTO da Dimastec, de forma prática, como construir um agente de IA a partir do guia “Como Construir um Agente de IA” — aplicando as 8 etapas do método a um caso real do projeto: o assistente técnico do Saturno-Calc / MYDAS (leitura de documentação, ADRs e código para apoiar a migração procedure → Java).

Resultado esperado da sessão:
    • CTO vê um agente em funcionamento aplicado ao contexto deles, não um guia teórico.
    • Valida o método das 8 etapas como padrão para os demais casos de uso da Dimastec.
    • Fecha um próximo passo concreto (piloto do assistente técnico read-only).

7. Passo a passo prático — construindo o assistente com Claude Code

Este é o roteiro de execução, na ordem, para levar o assistente técnico do Saturno-Calc / MYDAS do zero à produção — usando o ferramental que a Dimastec já tem (Claude Code + servidor MCP interno). Cada etapa mostra o que fazer, como fazer com o Claude Code e como isso é feito aqui no assistente-os (a referência de implementação que a Sousa Lima mantém).

Passo 0 — Setup, escopo e barreiras de segurança

Antes de qualquer código: definir limites logo de cara, porque assistente técnico é read-only e não pode tocar produção.
    • Propósito (1 linha): “Tirar dúvidas do time sobre o Saturno/MYDAS lendo documentação, ADRs e código — sem escrever e sem consultar banco de produção”
    • Critério de sucesso (o que define “funcionou”): resposta certa + cita a fonte (ADR/doc/código) de onde tirou.
    • Guardrails mínimos (kit de limites): proibido escrever em repositório/bancos, proibido dados de produção, sempre citar fonte; classificar o caso como IA aplicada (não-dados sensíveis) — alinhado à POL-IA-001 e à classificação de casos de uso da Dimastec.
    • Referência (assistente-os): cada “alma” (soul) declara propósitos e permissões em config; o runtime aplica allowlist de tools e nega o resto por padrão (fail-closed).

Passo 1 — System Prompt (o comando que define o agente)

No Claude Code, isto é o arquivo de instruções do projeto/agente (ex: AGENTS.md ou o prompt do subagente). É ali que mora a persona + regras.
    • Persona: “arquiteto sênior de Java que conhece o Saturno/MYDAS e responde em português com fonte”
    • Instruções: explicar a migração procedure → Java, citar camadas/patterns do hub (ex: DAO, @Secured, route handler), responder só com base no material indexado.
    • Guardrails em texto visível: nunca escrever, nunca acessar produção, dizer “não sei” se o RAG não achar, citar sempre a fonte.
    • Referência (assistente-os): o pool de prompts está versionado (CAMPO de prompts / prompt-garden) e a montagem é determinística — persona no início, sessão/RAG/histórico no fim.

Passo 2 — Escolher o modelo (LLM) com visão de custo

Documentação densa (ADR + código) pede janela de contexto ampla e bom raciocínio. Comparar 2–3 modelos antes de fixar.
    • Critérios: custo por 1M de tokens (entrada/saída), janela de contexto, latência, qualidade em português técnico.
    • No assistente-os, o roteador escolhe o modelo por tier e mede custo por chamada; no Claude Code, decide-se o modelo do agente e acompanha-se o custo do uso.
    • Entregável: tabela com 2 modelos (custo × contexto × nota), decisão registrada em 1 ADR.

Passo 3 — Ferramentas & Integrações (MCP)

A Dimastec já tem servidor MCP interno — este é o passo para conectá-lo. O agente ganha tools para ler ADRs, repositórios e base de conhecimento sem poder escrever.
    • Expor via MCP: busca na base de conhecimento (RAG), leitura de ADR, leitura de código — todas somente-leitura.
    • Referência (assistente-os): o kernel expõe ferramentas MCP sobre stdio com classificação de risco L1/L2/L3; a “alma/soul” só enxerga as tools na sua allowlist. No Claude Code, as ferramentas MCP entram no mesmo arquivo de configuração do projeto.
    • Teste na hora: uma chamada MCP ao vivo que busca um trecho de ADR e responde citando o arquivo.

Passo 4 — Memória (RAG + histórico)

O assistente precisa lembrar do contexto do projeto sem ter tudo no prompt a cada vez. Para isso, indexar ADRs, políticas e código em uma base vetorial e guardar o histórico da conversa.
    • Indexar documentos aprovados (allowlist): ADRs do Saturno, políticas (ISO 27001/LGPD/POL-IA-001) e trechos de código sanitizados — sem dados de produção.
    • Hispersistir o histórico por thread/sessão para conversas contínuas.
    • Referência (assistente-os): RAG com embeddings + re-rank opcional, cache semântico e limiar de relevância; quando não acha nada, o agente responde “sem contexto” em vez de inventar.

Passo 5 — Orquestração (o fluxo do agente)

Definir o caminho que o agente segue: entende a pergunta → recupera contexto (RAG) → decide se precisa de ferramenta → responde — com retry/tratamento de erro.
    • Modos por complexidade: pergunta curta → resposta rápida; pergunta com “passo a passo”/“análise” → fluxo mais profundo (fast/auto/pro como no assistente-os).
    • No Claude Code, o próprio agente já orquestra com tools; a decisão é quando ele pode chamar ferramenta e o que fazer em erro (limite de tentativas, timeout, dizer “não consegui”).
    • Referência (assistente-os): grafo LangGraph retrieve→generate↷tools com limite de iterações, streaming por etapa e escalonamento quando o contexto é fraco.

Passo 6 — Interface (como o time vai usar)

Definir onde o assistente aparece para o time técnico. Começar simples.
    • Fase 1: chat no terminal/IDE (Claude Code) sendo o próprio assistente com o prompt + MCP configurado.
    • Fase 2: interface web de chat para o time, com histórico por usuário.
    • Fase 3 (opcional): API para o fluxo de suporte existente.
    • Referência (assistente-os): chat via REST/WebSocket com streaming etapa-a-etapa e painel web — o CTO pode ver o grafo rodando ao vivo.

Passo 7 — Testes & Evals (qualidade mensurável)

Sem eval não há como provar que o assistente melhora ao longo do tempo. Criar um golden set de perguntas com respostas esperadas.
    • Montar golden set real do Saturno: ex. “qual o padrão de DAO multi-tenant?” → espera-se citar o ADR/pattern do hub; “todo endpoint precisa de @Secured?” → sim, pelos rules.
    • Medir recuperação: hit@1 (o doc certo aparece em 1º?), MRR, recall@5 — e fidelidade da resposta ao contexto (não alucinar).
    • Gate no CI: uma pergunta que não atingir o piso (ex: hit@1 ≥ 0.7) bloqueia o release antes de piorar em produção.
    • Referência (assistente-os): comando de avaliação de RAG com golden set, medindo hit@1/MRR/recall e saindo com código de erro se o piso não for atingido (a Dimastec já tem um golden set com 23 casos no hub — é o ponto de partida).

Sequência-resumo (8 etapas em 7 movimentos)

Escopo+guardrails → Prompt → Modelo → MCP → Memória → Orquestração → Interface → Evals. A ordem é pensada para o CTO ver valor rápido (MCP + RAG já respondem no dia 1) e segurança antes de escala (guardrails e evals desde o início). Cada etapa fecha com um artefato mínimo: ADR, prompt versionado, tabela de modelo, allowlist, golden set.
